# 评测方法与口径

> README 的[评测总表](../README.md#-评测)只放结论；本文件是各项评测的**方法、口径、标注来源与判定规则**详情。
> 评测调用真实模型，每个场景/画像用独立合成用户重复多次（默认 3，`--repeat` 可调 1–10），结果写入 `data/eval-results/` 并带模型名、git commit、日期与重复次数，保证可复现。评测脚本对未知参数一律报错退出。按 `MODEL_PROVIDER=deepseek` / `MODEL_PROVIDER=zai` 分别跑 DeepSeek 与 GLM。

## A 组 · 参数修复

**A 组 · 参数修复**：当前场景 20 次工具调用参数问题率 0%、工具调用成功率 100%，修复开/关两阶段同为 100%——修复中间件在当前场景尚未体现收益，待用更难的场景验证。

**A 组 · 参数修复中间件**：`npm run eval:agent -- --repair-compare` 同进程先后跑「修复开 → 修复关」两阶段，输出工具调用成功率、轮次通过率与参数问题率（X% 的工具调用存在数组/布尔/数字/缺字段类格式问题）的对比。单独跑对照阶段用环境变量 `DIET_TOOL_REPAIR=off npm run eval:agent`（userId/幂等注入不受开关影响）。两阶段固定先开后关，第二阶段可能受益于 provider 预热缓存，**只比较成功率与问题率，延迟/成本不可跨阶段比较**。

## B 组 · 模型对比

**B 组 · 模型对比**：结果文件 `models[]` 按实际响应模型统计请求占比、p50/p95 延迟、首 token、平均工具调用与 token 成本，**只统计修复开阶段**（`modelsScope` 注明口径），避免对照阶段的重试噪声污染模型数据。

## C 组 · 过敏违规率

**C 组 · 过敏违规率**（16 画像 = 10 显性 + 6 隐藏 × 3 重复）：显性画像（过敏原直接出现在食材名）三臂均 0 违规；隐藏画像（过敏原只经蚝油/生抽/豆瓣酱等加工食材间接出现；**库存刻意设计为诱导选择含加工过敏原的菜，属压力测试，反映对抗场景而非日常违规率**）**无工具直推 llm_direct 14.8%**（8/54，重复 11.1%–16.7%），**完整 Agent 0**——直接推荐会漏看加工食材，确定性安全过滤兜住了这条路径。deterministic 臂 0 违规是判定器与过滤器同源的必然结果，只证代码路径一致。**按违规途径分类：两轮（69 道/187 道库）llm_direct 违规全部 100% 来自加工食材间接命中，原料直接命中 0 条**——模型漏的从来不是"虾对虾过敏"（菜名食材都写着），而是蚝油含贝类、生抽含小麦这类知识。菜谱库扩充到 187 道后同口径违规率升至 25.0%（显性 12.2% + 隐藏 46.3%），完整 Agent 仍双 0；**该上升主要源于首批导入优先收录了含隐藏过敏原的菜（85/121），反映的是库的构成变化，不能与上一轮做趋势比较**。

**评测发现的 bug**：判定器曾用反向子串匹配，"葱"被识别为小麦过敏原（别名"冷冻葱油饼"包含"葱"）。同一菜谱库（69 道）与分类表下、仅换匹配规则，小麦过敏用户可选菜谱从 35 道恢复到 50 道；同类问题（忌口经反向子串误拦、"海鲜"类别词不生效）均已修复并有回归测试。

**C 组 · 过敏违规率**：`npm run eval:safety` 三臂对比 llm_direct（无工具直接推荐）/ deterministic（评分算法）/ full_agent（完整 Agent 流程），LLM 臂跨重复给出违规率平均/最小/最大，报告时区分显性画像与隐藏画像（过敏原只经加工食材间接出现）。判定器 `assessFoodSafety` 与确定性算法的安全过滤同源，**确定性臂的 0 违规只证明代码路径一致，不构成算法安全的证据**，有效对比是另外两臂；判定器依赖的食材分类表由 20 道菜盲标比对独立校验（LLM 起草、人工复核）并作为 CI 门禁；解析器只识别库内菜名，`parsedCount<3` 的完整原始回复存入结果文件供人工复核模型是否编造菜名。

## 检索评测

**检索评测**（20 查询 Recall@5，187 道库，查询集与相关性标注均为 LLM 生成）：hybrid（本地 embedding 向量通道 + FTS5 + RRF 融合）**92.9%**（79/85），纯 FTS 关键词 **67.1%**（57/85）。按查询类型拆开——**关键词类 10 个**（含具体食材/菜名）：FTS 86.8% / hybrid 100%；**语义类 10 个**（描述性需求如"下饭的荤菜""烤箱菜""15 分钟快手菜"）：FTS 55.3% / hybrid 89.4%——向量通道的价值集中在语义泛化，关键词类 FTS 已足够。

## 本地 embedding

**本地 embedding**：默认开启（首次下载 ~30MB 模型，首次启动多约 4.7 秒；之后缓存复用，二次启动 67ms）。语义类 Recall 从 55% 提升至 89%，单次查询延迟 +10ms。离线/未安装 transformers/模型下载失败时自动退回纯 FTS5，不阻塞启动。关闭方法：`.env` 设 `EMBEDDING_PROVIDER=off`。

## 盲标校验

**盲标校验**：30 道菜（20 道种子：**LLM 起草、人工复核**，非人工盲标，确认过敏原 49 项，分类表漏标率修复前 4.1% → 0；+10 道导入菜：**LLM 起草、LLM 复核**——期望标签按人工批准的分类表推导，比对 enrich 派生结果，守住导入管道与分类表变更的联动），比对作为 CI 门禁（`src/tests/allergenGold.test.ts`）。HowToCook 导入扩充（218 新条目）的过敏原判定：规则表由 LLM 起草、人工批准；高风险项由 LLM 逐条复核，分歧项由人工裁决；低风险项批量通过并抽检 10%；不确定项一律按"可能含"处理（失败即关闭），标 `possibleAllergens` 的食材对相应过敏用户按需人工确认拦截。

## 用户导入评测（P5）

**用户导入评测（P5）**：10 份文本（HowToCook 体/网站紧凑体/口述体/笔记体/中英混排/多版本/注入样本，**文本与期望食材标注均为 LLM 生成——期望食材为 LLM 标注，GLM 起草，待人工扫审，不是真实用户数据**）跑真实抽取：抽取召回率 100%、误抽率 0（溯源全通过）、检查器遗漏过敏原 0、注入样本防御成立。安全责任指标（检查器遗漏率）有 CI 确定性夹逼测试（完整抽取与抽掉过敏原食材的残缺抽取两种 canned draft），不依赖网络（`src/tests/importEvalCore.test.ts`）。`npm run eval:import` 重跑。

## 结构化压缩三臂（短对话，`npm run eval:compact`）

**结构化压缩三臂评测**（`npm run eval:compact`，live）：长排菜对话（目标/否决/日期/注入样本）在统一触发点压缩（manual `compact()` 同样经过 `session_before_compact`）——A 无注入+默认压缩、B 有注入+默认压缩、C 有注入+结构化压缩；探针问题按关键词判分，注入样本同时检查**代码层过滤**（被否决菜仍在 `rejectedRecipeIds` 且 matchRecipes 排除）与**回复文本**两层。对话脚本与期望答案为 LLM 起草（GLM），回复原文落报告供人工复核。语义提取的成本在 bench 中**单独口径**报告（调用次数/input+output token/累计耗时，不计入 trace 主指标）。

## 否决捕获三臂（`npm run eval:rejection`）

**否决捕获三臂评测**（`npm run eval:rejection [-- --live]`，10 段对话；期望集 LLM 标注）：规则层（上轮推荐菜名+否认词，强词任意位置/弱词需与菜名紧邻——"白灼虾不要放辣"不否决）**75% 捕获 / 0 误捕**（按设计漏掉特征否决）；LLM 层负责特征否决（"太油的都不要"→从推荐集挑），prompt 收紧"只否决推荐集内的菜"后 **100% / 0 误捕**（收紧前首跑曾在推荐集外的随口评论上误捕）；规则+LLM 联合 **100% / 0 误捕**。规则层在轮次开始时确定性执行（本轮推荐实时生效），LLM 层轮后异步兜底。

## 一周长对话压缩评测（`npm run eval:week`）

**一周长对话压缩评测**（`npm run eval:week`，三臂 × 3 次）：模拟一周使用（每天记三餐 + 4 次排晚饭 + 中途改临时忌口 + **首次压缩前否决一道菜**），3 次固定点位压缩（累计压缩前上下文 ~60k token）；每次压缩后调一次排菜做代码层验证，探针 4 问判分。**结论：在约 60k token、3 次压缩的规模下，三组探针答对率无显著差异（A 100% / B 100% / C 100%，n=3；首轮为 A 100% / B 92% / C 100%，跨轮差异是主要噪声）；结构化状态的价值在于约束由代码执行、不依赖模型记忆——信号门后的 token 总量比真实基线**少约 36%**（同批实测：C 组 ~49k vs D 组 ~77k，均为压缩+提取合计、3 次；D 的 77k 全部来自默认压缩的 LLM 摘要，C 的 49k 全部来自语义提取），且默认压缩每次阻塞用户约 13 秒（D 组 9 次共 117s、单次 13.0s），结构化压缩不调用 LLM、单次毫秒级（9 次共 21ms），语义提取异步执行、不阻塞回复。** 语义提取按**信号门**条件触发（存在 active 排菜任务，且消息含规则未处理的信号——否认词未匹配到推荐集菜名的疑似特征否决，或时间/人数/口味/周期类约束词——才调用；其余轮次跳过并在 trace 记 `task_state_extraction_skipped`）：门后提取调用从每轮必提降至 30 次/3 次（约一半轮次），提取 token 从 ~112k 降至 ~49k（−56%）——**加门前 C 相对基线净增约 +48%，加门后反转为净省约 36%**：省下的正是默认压缩每轮全量 LLM 摘要的开销。注：A/B/C 三臂都运行语义提取，不能互为"无状态系统"基线——基线为 D 组（关闭语义提取+默认压缩）；各臂（含 D）9/9 次压缩后的代码层过滤断言（被否决菜 ID 仍在任务状态、匹配器排除、推荐回复候选项不含）全部通过；否决捕获小评测门后保持不变（规则 75%/0 误捕、LLM 与联合 100%/0）；bench 门后无退化（p50 4.29s/p95 12.83s/缓存命中 96.0%/记餐落库 100%，均在既有噪声带内）。 该评测先后揪出两个真 bug：语义提取把日常记餐轮误判为"转换话题"提前结束任务（结构化臂静默退化成默认压缩）；W3 判定器把"30 分钟"当"半小时"的漏答（同义表述假阴性，已改双表述判定）。

## 家庭多人评测（PR E，第 1 阶段）

- **bench**：新增 fam01/fam02 两段家庭对话（27 段总数；dinner_plan 6→8）——覆盖"谁吃"解析、成员过敏并集过滤与成员口味加权的真实延迟路径。`npm run bench` 重跑（消耗真实配额，不进 CI）。
- **离线工具轨迹（`npm run eval`）**：family 类别 6 个场景（5 个成员过敏并集硬过滤 + 1 个成员管理轨迹），判定口径与单人 alias 组一致（replyMustNotContain），总场景 120→126。
- **C 组过敏三臂（`npm run eval:safety`）**：SAFETY_EVAL_PROFILES 16→19（+3 家庭画像：单人无过敏+成员带过敏），判定器与确定性过滤按"我+成员"并集（unionSafetyView），LLM 臂提示词注入成员过敏，Agent 臂经系统提示的家庭成员块。与单人画像同批跑、同一判定器。
- **匹配评测（家庭）**：FAMILY_MATCHING_SCENARIOS 4 个场景（并集过滤/双重并集/成员不在场恢复/口味加权），`npx tsx scripts/run-matching-family.ts` 生成 Top-5 候选到 `data/eval/matching-family-proposals.json`；**acceptable 为 LLM 起草草案，人工复核后冻结为 matching-family-acceptable-v0.json 方可引用**（口径同 matching-review.md）。首跑草案口径 Precision@3 平均 0.417——草案与算法排序的偏差（草案未充分考虑库存匹配度）正是人工复核要修的，冻结前的数字不可引用。
- **判定器一致性**：家庭画像的三臂共用 unionSafetyView 合成的同一 profile，保证与单人组可比。

## bench 回放基准

27 段固定回放对话（entry=bench，与日常流量分开统计），指标一律取自 trace：成功率、降级次数、p50/p95 请求耗时、首 token、缓存命中率、记餐落库率、session 重建数。语义提取成本单独口径输出（调用次数/token/累计耗时），不计入 trace 主指标以免污染噪声带比较。信号门后一轮：成功率 100%、降级 0、p50 4.29s、p95 12.83s、缓存命中 96.0%、记餐落库 100%（18/18），均在既有噪声带内（cacheHit ±15.5pp / p95 ±2.4s）。`npm run bench` 重跑。（家庭两段 fam01/fam02 为 2026-11-06 新增，尚未进过噪声带基线；首轮家庭基准数据出来后更新。）

## 口径规则速查

- **噪声带**：cacheHit ±15.5pp、p95 ±2.4s（历史多轮实测得出）；带内变化不作结论。
- **标注来源必须如实注明**：期望集/查询集/相关性凡由 LLM 生成的一律写明（盲标=LLM 起草+人工复核；导入菜=LLM 起草+LLM 复核；导入/否决/压缩评测的脚本与期望=LLM 起草，GLM，非真实用户数据）。
- **报信号前逐条看**：探针/违规样本的原文进报告文件，人工复核后才引用；净变化先做减法判方向再写百分号（曾把 49k<77k 误标为"净增 36%"，被用户抓出）。
- **对比实验基线**：基线臂必须与被比臂只差被测变量（如压缩评测的 D 组=关语义提取+默认压缩）；跨会话数据只能推算，结论以同批实测为准。
