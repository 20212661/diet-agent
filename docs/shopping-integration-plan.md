## 1. 目标与默认决策

围绕下班做饭场景，连接「菜单 → 缺少的食材 → 在线采购 → 收货 → 库存」，减少在饮食工作台和购物 App 之间反复整理清单的操作。

默认按个人本地使用设计，优先购买生鲜食材，首批支持美团和淘宝闪购。成品外卖推荐、佣金经营、多人公网服务留到独立需求阶段。

采用分阶段路线：

1. MVP：结构化采购任务、复制清单、经过验证的平台入口或二维码、手动记录已下单、识别收货清单并确认入库。
2. 官方能力增强：取得权限后接入联盟 API，获取允许范围内的店铺、商品和购买链接。
3. 自动选购实验：在独立实验分支验证界面自动化搜索和加购，用户核对购物车并完成购买。
4. 完整交易接入：仅在获得消费者交易能力的明确授权和文档后设计创建订单、支付及订单状态同步。

第一版的成功标准是可以走完真实购买和入库流程；复制清单与打开平台仍然需要用户在平台内选购，不标记为自动购物。

## 4. MVP 用户流程

### 4.1 创建采购任务

库存页面增加“去采购”，周计划缺料清单增加“创建采购任务”。用户勾选食材，检查名称、数量、规格、期望购买日期，选择平台。

示例：番茄 500 克、鸡蛋 1 盒、鸡胸肉 400 克。未指定鸡蛋盒装数量时不自动折算为个数。第一次不要求地址和手机号，平台负责配送信息。

创建任务保存待购条目的 ID 与版本、计划来源、名称和数量快照。已有未完成任务包含同一条目时提示关联，避免无意重复采购；用户可以明确创建额外采购。

### 4.2 去平台购买

采购任务页显示清单、复制按钮、平台入口和二维码。优先使用经过核验的 HTTPS 平台链接；二维码只编码平台外部链接，不包含 localhost、用户画像或完整采购清单。

二维码不负责把电脑清单传到手机。第一版电脑保留清单供对照，用户也可截图；跨设备同步清单是另一个需要可访问服务的功能。

打开平台、展示二维码、复制清单只记录交接动作，不代表已下单。用户买完回到页面，选择实际买到的条目并点击“记录已下单”，可填写可选的外部订单号和金额。金额标记为用户填写，来源不冒充平台数据。

### 4.3 收货与入库

打开对应任务，上传小票、商品清单图片或粘贴文本。识别结果进入草稿，用户确认实际收到的食材、数量、储存位置、替代品和未收到的项。

确认前明确显示“新增库存 / 与已有库存合并”的结果。有兼容单位的精确数量才允许相加；“一盒”和“10 个”等不能无依据转换。无法合并时让用户选择独立批次或填写合并后的数量。

同名同储存位置的新批次应能独立保存，不能继续被旧去重逻辑覆盖。实施时为库存添加可选采购批次/收货来源标识，普通旧条目保持兼容；旧批量导入和整表编辑必须保留这些标识。

在一个数据库事务中完成收货记录、库存变更、任务状态和待购项更新。只移除已完全满足且仍与创建时版本一致的待购项；剩余项继续待买。清单被编辑或移除时提示重新核对，不能删掉用户后来增加的需求。

支持分批收货、少送、缺货、替换和取消未履约项。已入库后的退款或丢弃通过库存操作处理，第一版不做自动退款联动和自动撤回库存。

## 5. 状态与数据模型

采购状态独立于 `IngredientStatus`，已下单的食材仍不可用于做饭。

### 5.1 状态机

- 条目状态：`pending`（待买）、`ordered`（用户记录已下单）、`partially_received`、`received`、`cancelled`。
- 任务状态由条目汇总：全部待买为 `draft`；全部有效条目已下单且无收货为 `ordered`；待买与已下单混合为 `in_progress`；出现收货但尚未全部终结为 `partially_received`；全部收到或取消且至少有收货为 `completed`；全部取消为 `cancelled`。
- 已收货的部分不能被取消覆盖；部分条目已收货后只能取消剩余需求，保留实际入库历史。
- 跳转购买是事件，不改变条目状态。允许直接从待买登记收货，兼容线下采购和忘记记录下单的情况。
- 数量未知或不可换算时，是否完全满足由用户核对确认，不能自动计算。

### 5.2 建议新增表

| 表 | 主要字段 | 用途 |
|---|---|---|
| `shopping_tasks` | id、user_id、title、provider、status、source、version、created_at、updated_at | 采购任务与来源 |
| `shopping_task_items` | id、task_id、user_id、source_inventory_item_id、ingredient_id、name、requested_amount_text、quantity、unit、specification、status、source_snapshot_json | 保留采购需求快照和来源，结构化数量可为空 |
| `shopping_handoffs` | id、task_id、user_id、provider、target_type、url、expires_at、verified_at、created_at | 平台交接记录，敏感追踪参数按需保留 |
| `shopping_receipts` | id、task_id、user_id、operation_id、source_type、confirmed_at | 一次确认收货的批次 |
| `shopping_receipt_items` | id、receipt_id、task_item_id、actual_name、actual_amount_text、quantity、unit、inventory_item_id、resolution | 实收条目、匹配及库存关联 |
| `shopping_events` | id、task_id、user_id、type、details_json、created_at | 状态来源和必要审计记录 |
| `shopping_provider_settings` | user_id、provider、enabled、entry_url、verified_at、verification_note | 各用户平台入口配置 |

数据库外键/约束校验任务与条目的归属；查询和更新同时带 user_id。收货业务唯一键建议使用 `(user_id, task_id, operation_id)`，即使换了路由也不能重复提交同次收货。对“同一张图新建 operationId”提供重复候选提示，允许确认为真实的第二次购买。

金额如需保存，使用整数分；数量保留原文，换算结果记录依据。平台链接和商户标识可能过期，不作为食材的永久 ID。

## 6. 模块与平台适配层

建议增加：

```text
src/shopping/
  types.ts                       # 采购、数量和能力类型
  quantity.ts                    # 精确解析、单位兼容、合并规则
  shoppingService.ts             # 建单、记录下单、收货、取消
  providerRegistry.ts            # 能力与适配器注册
  linkValidation.ts              # 链接及过期校验
  providers/manualProvider.ts    # 已验证入口，无凭证模式
  providers/meituanProvider.ts   # 第二阶段，实际权限支持的功能
  providers/taobaoProvider.ts    # 第二阶段，实际权限支持的功能
src/store/repositories/shoppingRepository.ts
src/web/routes/shopping.ts
public/shoppingView.js
```

能力矩阵包括 `entryLink`、`storeSearch`、`productSearch`、`productLink`、`cartWrite`、`orderCreate`、`orderStatus`。能力可处于未配置、未验证、可用、不可用；只有实际验证可用时才显示对应操作。

第一版手动适配器只提供入口。联盟适配器按实际授权暴露查询和取链，不预设 cartWrite/orderCreate 为可用。避免所有平台强制实现一个实际上没有权限的接口。

第二阶段候选商品需带店铺、商品标识、规格、价格来源、更新时间和跳转目标；无法核实规格、成分或配送范围时标记待核对。排序优先满足食材/规格需求，其次预算和配送条件，不按佣金优先。

| `GET /api/shopping/providers` | 查询配置和实际可用能力 |
| `PUT /api/shopping/provider-settings/:provider` | 保存平台入口配置 |
| `GET /api/shopping/tasks` | 当前用户任务列表，分页和状态筛选 |
| `POST /api/shopping/tasks` | 从待购清单或手动输入创建任务 |
| `GET /api/shopping/tasks/:id` | 获取任务、条目、收货摘要 |
| `PATCH /api/shopping/tasks/:id/items/:itemId` | 编辑未履约的需求，已有履约部分保持历史 |
| `POST /api/shopping/tasks/:id/handoffs` | 获取已验证交接目标并保存记录 |
| `POST /api/shopping/tasks/:id/mark-ordered` | 手动标记选定条目已下单 |
| `POST /api/shopping/tasks/:id/receipt-preview` | 复用识别逻辑，生成关联候选，不写库存 |
| `POST /api/shopping/tasks/:id/receive` | 用户核对后原子收货入库 |
| `POST /api/shopping/tasks/:id/cancel-items` | 取消指定条目的未履约需求 |

所有持久化变更使用 operationId；更新使用 expectedVersion，涉及库存时携带 inventoryUpdatedAt。冲突返回 409，归属不符按不存在处理，数量或状态非法返回 422。无当前库存行时也要定义稳定的缺省版本契约，不能依赖每次读取产生的新时间戳。

扩展现有中间件：新动态路径和 PUT 必须接受相同的 Host、Origin、JSON、用户身份检查；目前用户身份写入检查只覆盖 POST/PATCH/DELETE，需同时补齐 PUT 或实施时统一改用已有受保护的方法。

同步数据库写入使用现有 writeOnce。平台 HTTP 调用在事务外完成，结果成功后短事务落库；未来远端下单不能放进这个同步 writeOnce，需要另行设计持久操作状态、平台幂等键和未知结果核对。

## 8. Agent 与页面交互

MVP 先完成页面闭环，再接入 Agent，避免模型在购物功能尚未落地时承诺购买成功。

建议 Agent 工具：查询采购任务、从已有清单创建草稿、获取平台交接入口。所有工具使用当前会话用户身份，不能接受模型任意指定 userId。

“已经买好了”可以生成待核对的下单记录；“帮我买”生成采购任务和购买入口。模型不能仅凭打开链接就宣告下单成功。收货图片必须进入可编辑预览后由用户确认。

页面增量：

- 库存页待采购区增加勾选与“去采购”；周计划沿用缺料展示，增加任务入口。
- 采购任务列表显示状态、平台、创建时间，区分用户记录与平台核实的信息。
- 任务详情包含清单、购买入口、二维码、已下单记录和收货面板。
- 默认放在库存页面内，第一版不额外占用新的全局快捷键。

## 9. 数据处理与运行要求

沿用本地数据策略。平台密钥如需接入，仅由服务端读取配置，不进入页面或模型上下文；链接处理仅接收已验证的 HTTPS 域名，拒绝脚本协议和 localhost 等内网目标，短链需要验证实际落地平台。

第一版不在服务端抓取用户任意输入的 URL，避免链接验证变成任意网络请求。官方适配器仅访问固定官方 API 主机。二维码优先本地生成，选库时核实维护状态、许可和 npm audit 结果。

新增采购记录纳入 `/data`、`/diet-export`、`/delete-data`、迁移备份清理范围；用户操作日志不保存密钥、完整地址、手机号和完整图片。图片默认作为临时识别输入，不长期保存，沿用现有视觉模型发送提示。

平台回调需要外网可达端点，当前本地服务不具备该条件。第二阶段优先使用获准的查询接口；需要回调时单独设计认证、签名、重放防护及最小云端中继，不通过开放本机绑定解决。

## 10. 实施里程碑与交付物

以下是单人开发有效工作日估算，不含平台审批、用户账号操作或商务等待。预计 MVP 约 7–11 个工作日；根据任务复杂度可调整。

| 阶段 | 预计投入 | 工作与交付 | 进入下一阶段的条件 |
|---|---|---|---|
| M0：能力验证 | 0.5–1 天 | 两个平台能力核验表；至少一个可用入口；确认实际手机终端和生鲜场景 | 有真实可用交接目标或明确退化方案 |
| M1：采购数据和服务 | 1.5–2 天 | 状态机、SQLite 迁移、仓储、版本与幂等、创建及查询接口 | 旧库可升级，跨用户访问失败，任务状态正确 |
| M2：购买交接页面 | 1–1.5 天 | 待购勾选、任务详情、复制、链接、二维码、手动记录已下单 | 真实终端可打开入口；跳转不改变订单状态 |
| M3：收货与库存一致性 | 2–3 天 | 图片预览关联、数量核对、批次保存、原子入库、待购清单核销 | 重试不重复入库，部分收货和并发编辑处理正确 |
| M4：Agent 和数据生命周期 | 1–1.5 天 | 查询/建草稿工具、提示词、导出与删除、错误恢复 | 聊天和页面状态一致；数据导出删除完整 |
| M5：验证与交付 | 1–2 天 | 单测、API/UI 冒烟、真实采购演练、文档 | 下列 MVP 验收全部通过 |

M1–M5 可在平台审批未完成时推进。M0 的真实终端验证需要用户账号和手机配合，届时提供可测试的具体入口和步骤。

第二阶段预计另需 3–6 个开发工作日，从实际获得权限和样例算起。依次完成官方签名客户端、店铺/商品覆盖验证、取链缓存与过期、页面推荐、故障降级；如果只有餐饮供给而没有生鲜，保留入口并记录范围，不把它当成买菜搜索。

第三阶段先用 1–2 天做可行性实验：选一个平台和一个实际可用终端，搜索 3 类食材并准备购物车，停止在用户可审阅的位置。依据登录稳定性、规格准确率、已有购物车处理和重复操作风险，再决定是否产品化，工期另估。

## 11. MVP 验收和测试

### 核心验收用例

1. 从周计划将缺料加入待购清单，创建采购任务；数量缺失保持待确认。
2. 复制清单与显示平台二维码成功，手机能打开经过核验的入口；不存在把 localhost 编码进二维码的情况。
3. 打开链接后任务仍为待买；用户选择两项记录已下单后状态正确，第三项仍待买。
4. 已下单但未收货的食材不进入可用库存，菜谱仍认为它缺失。
5. 图片识别失败可改为粘贴文本或手动填写；预览及取消不改库存。
6. 完整收货后库存更新、任务完成、对应待购项核销；缺货项保留待买。
7. 少送、替换品和分批收货可表达；不兼容单位不自动相加；不同采购批次不被同名去重覆盖。
8. 同一 operationId 双击、超时重试、重启恢复只产生一次收货；同一 ID 不同内容返回冲突。
9. 从第二个标签页修改库存或需求后，旧收货提交返回冲突，用户刷新核对后可重新提交。
10. 错误用户、跨站写入、非法链接被拒绝；新 PUT 路由受同样检查。
11. 旧数据库迁移后原有库存、周计划、饮食记录仍可读；导出包含采购数据，删除不影响其他用户。
12. 无官方 API Key、平台链接过期、平台请求失败时，仍可复制清单、手工记录和收货入库。

### 验证执行

- 为数量兼容、状态转换、收货原子性、幂等、并发冲突、用户隔离和迁移编写针对性 Vitest 测试。
- 扩展 `scripts/web-smoke.mjs`，覆盖真实 HTTP 写入流程和安全校验。
- 修改页面后验证宽窄屏、复制失败提示、二维码清晰度以及双击提交；至少一次真实手机扫码购买演练。
- 执行 `npm run typecheck`、`npm test`、`npm run build`、`npm run test:build`、`npm run test:web`、`npm run test:package`；沿用 Windows/Linux、Node 22/24 CI 检查。
- 官方 API 用固定样例做离线测试，独立进行真实账号联调，明确区分样例成功与实际权限可用。

## 12. 风险、依赖与应对

| 风险 | 应对和决策 |
|---|---|
| 消费者加购或交易 API 无权限 | 第一版不依赖此能力；验证后再扩展 |
| 联盟接口仅覆盖活动、餐饮或部分商品 | 在能力矩阵和页面体现，买菜保留平台入口 |
| 链接过期或不同终端行为不一致 | 保存核验日期与期限，提供复制清单与重新配置 |
| 数量文本不能准确运算 | 保留原文与用户确认，不估算包/盒/把的重量 |
| 收货覆盖已有库存、重复入库 | 来源批次、业务唯一键、版本检查和事务 |
| QR 能打开平台但不能传采购清单 | 明确交接作用；跨设备清单同步另立需求 |
| 自动化误加规格、重试重复加购 | 第三阶段保存购物车前后差异，遇未知结果先核对；不自动清空已有购物车 |
| 公网回调与本地架构不兼容 | 查询优先，需要回调时另行设计中继 |

实施前可以由开发者自行确定的选择：模块命名、页面布局、二维码库、迁移版本和内部数量表示。

影响路线且需要用户提供的信息：实际手机系统、常用购物平台和配送城市；是否已有开放平台账号/API 权限；未来偏个人自动化还是对外产品。这些信息不阻塞当前计划和无权限 MVP 的数据层开发。

## 13. 推荐开发顺序与完成定义

先核验入口，再实现采购任务，随后交接购买、收货原子入库，最后接入 Agent 和数据生命周期。不要先写无法联调的自动下单接口。

MVP 完成定义：两个平台都有明确的可用/待配置状态，至少一个平台完成真实购物演练；从缺料创建任务到实收确认入库全流程可用；关键一致性、安全、迁移和包装检查通过；没有把用户手动记录误呈现成平台自动核实。

完成 MVP 后，以真实使用反馈决定下一步：主要痛点是找店铺和商品则申请官方查询/取链权限；主要痛点是重复搜索与加购则开展自动选购实验；需要在项目内直接结算则先确认平台商务合作和消费者交易权限。
